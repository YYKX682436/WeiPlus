# WeKit 单功能分析、执行与验收

本工作流以用户确认的实际需求为边界。主脑负责方案与验收，Codex 负责已确定方案的执行与本机取证；遇到会改变行为的事实冲突，返回具体证据，不让执行者临时发明另一套方案。

## 1. 把功能名变成可验收行为

讨论窗口先用一句话写明：**谁在什么场景做什么操作，Hchat 应产生什么可见结果**。再补齐本功能实际涉及的条件，例如私聊/群聊、自己/他人、前台/后台、开关状态、当前页面、过滤对象、失败时行为。

不要把上游功能描述当作用户全部需求。例如：

- 「屏蔽来电铃声」「拒接来电」「不展示来电但让对方自然超时」是不同功能；上游 `BlockVoipRingtone` 不自动等于后两者。
- 「已读追踪」需要解释数据从哪里来，不能把外部链接访问或来源 IP 统计当作微信真实已读状态。
- 「自动勾选原图」「查看时自动下载原图」「发朋友圈尽量减少压缩」分别发生在不同流程。
- 「本地余额显示修改」不代表真实资金变化。沿用现有功能边界，不扩大为支付协议修改。
- 「其他人可以触发链接解析的聊天」与「我自己发送链接是否触发」分开确认，不能把两种消息来源混成一个开关条件。

已有信息足够时由主脑作出具体设计；只有缺失答案会显著改变产品行为、外部依赖或实施范围时才问用户。

## 2. 收集双方最小完整调用链

### WeKit 来源卡

每次记录仓库、完整 commit、功能中文名、`technicalId`、类名、入口路径和固定 SHA permalink，并跟踪：

1. 入口：`startup`、`onEnable`、`onClick` 等实际入口；`ClickableFeature` 可能没有开关。
2. 定位：`IResolveDex`、委托属性、字符串/签名/结构锚点、期望匹配数量和缺失条件。
3. 执行：Hook 前后逻辑、原方法调用、UI 修改、消息/数据库/网络副作用。
4. 数据：配置 key、默认值、状态机、缓存、账号与进程归属。
5. 依赖：实际调用到的 API、工具类、资源、JNI、子模块、扩展包或独立服务器。
6. 生命周期：线程、挂起工作、监听器、页面/会话切换、关闭/销毁时如何结束。

`feature-index.json` 的直接依赖来自静态扫描，只用于缩小阅读范围。间接依赖、同包辅助类、通配导入、反射字符串、动态注册和调用结果必须继续核查。不能把「读完入口文件」写成「完整分析完成」。

### Hchat 接入卡

读取当前 Hchat，记录本次目标 HEAD 与相关未提交改动，而不是回退到本资料的历史基线。按 [接入地图](HCHAT_INTEGRATION.md) 判断：

| 问题 | 必须给出的具体结论 |
| --- | --- |
| 已有相近能力吗？ | 原功能 ID/路径、相同行为、差异；选择复用、增强或新增 |
| 共享 API 能用吗？ | `WeChatApis` 的具体入口和能力条件；不足时具体新增点 |
| 新 Feature 放在哪里？ | `hooks/items/<feature>/` 的文件和职责；是否需要在 `FeatureRegistry` 登记 |
| 用户怎样打开？ | 设置存储、Provider、分组 ID、Miuix 页面路由和可见入口 |
| 怎样定位宿主？ | 现成 API 或目标版本已确认的定位规则；缓存归属和失效方式 |
| 谁安装/清理 Hook？ | 共享拥有者、订阅/租约、代次检查、异步任务与页面监听清理 |
| 失败如何处理？ | 模块失败与宿主异常分开；是否已经产生不可重复的副作用 |

同一微信方法可能已经被其他功能 Hook。先查现有注册与共享 API，不以“上游这样写”作为重复安装的依据。禁止为迁移方便恢复旧 API、创建第二套模块入口或复制整套上游底座。

## 3. 宿主适配证据

上游定位规则是研究起点。微信混淆类名、签名、资源和消息结构均以实际目标 APK 为准。先复用当前 Hchat 已确认的实现和证据，再补缺口。

需要新增或改变内部定位时，记录目标 APK 的 SHA-256、实际包名、versionName/versionCode、渠道/构建标识、可获得的 clientVersion 与 Tinker/热更新信息，并提供实际类/方法/字段签名、匹配数量和调用关系。不要猜参数位置、表结构、Intent key、资源 ID 或消息协议。

本机 DexSQL/MCP 或反编译工具用于静态取证；它们不是 Hchat 的 APK 运行依赖。若讨论窗口无法使用本机工具，先生成一个只读取证任务，精确列出查询问题、候选锚点、需要返回的调用链和输出格式。Codex 返回后主脑再定实现，不要求执行者替主脑补关键设计。

遵循 Hchat 现有缓存与热更新隔离：使用 `DexMethodCache`/相应现有缓存体系的真实 runtime key，缓存命中不重复全量扫描。宿主 APK 或已加载运行时代码身份变化时，按现有身份策略使对应缓存失效；仅 ClassLoader 代次变化时，用当前 ClassLoader 重新解析并验证描述符、重绑定受影响的运行时对象。不要把 ClassLoader 对象 hash 加入持久缓存 key，也不要因此一律全量重扫。两者的区分见 [WeChatVersionApi](https://github.com/YYKX682436/WeiPlus/blob/332c9650103fa68fc5f755d4c2d8cef4502d0c34/app/src/main/java/h/Hchat/hooks/api/runtime/WeChatVersionApi.java#L172-L177)。零匹配、多匹配、反射解析失败分别解释，不用取第一个匹配或放宽约束制造成功。

按结构和能力识别可用路径。不得仅因本次验证了一个 versionCode 就对其他所有版本新增全局拒绝；未验证的范围明确记录。

## 4. 主脑给用户的方案

建议输出以下内容，篇幅随功能复杂度调整：

1. 用户最终能得到的行为、开关位置和生效方式。
2. WeKit 来源、当前实现质量/未完成标记、必要依赖。
3. Hchat 已有能力与拟接入方式，明确保留/替换/删除的具体代码。
4. 已有证据、仍需本机取证的具体问题。
5. 有限且与改动相关的验收场景，包含重要负向场景。
6. 第一人称、可直接复制的 Codex 指令；额外说明用户是否需配合、难度 1–5 星、是否开新窗口和白话总结。

来源归属与许可是具体选中文件的事实检查：保留作者/许可证声明、固定链接和修改说明；涉及 GPL 代码合并和分发时核实覆盖范围及对应源码交付，不能只加一个致谢代替。不要自动替全部 Hchat 作者作重新许可决定。完整背景见 [来源边界](SOURCE_ARCHITECTURE.md)。

## 6. 与改动相关的验收

按功能选择最有证明力的项目，不为小改动机械重跑全仓库；不要以字符串存在测试代替真实调用链验证。

| 验证层 | 能证明什么 | 不能据此声称什么 |
| --- | --- | --- |
| 静态阅读/差异审查 | 调用关系、潜在分支、来源和设计一致性 | 真机触发过或微信服务器接受了 |
| APK 静态定位 | 该 APK 中匹配目标、结构和签名 | Hook 生命周期、用户体验正确 |
| 生产逻辑回归 | 被实际执行的规则/边界在给定输入下正确 | 所有宿主版本都支持 |
| Debug / Release / Lint | 可构建、受检查的规则、R8 后结构 | 功能在真机已生效 |
| 真机观察 | 指定设备/框架/API/宿主版本的指定场景 | 没测的设备、账号、渠道和外部结果 |

具体关注点按需要选取：

- 默认关闭、开关切换、设置持久化、关闭后排队任务不再触发；必须重启的情形须有原因。
- 私聊/群聊、自己/他人、目标/非目标聊天，匹配与不匹配均有观察结果。
- 页面进出、切换会话、返回、切换账号、重启进程、主微信/分身微信缓存隔离。
- 同方法重复初始化、旧代次回调、共享订阅销毁、异步回调晚到；没有重复发送或重复 UI 修改。
- 对 UI 功能核对 Activity/页面归属，输入法、长内容、尾行、手动浏览历史等实际受影响场景。不要刷新不相关联系人选择页的 RecyclerView。
- 缓存命中、缓存丢失、宿主/热更新变化、定位失败；不把昂贵扫描放入热回调。
- 有副作用的操作分别记录“识别到”“请求入队”“服务端成功”“实际展示”，不互相替代。

真机遵循 Hchat AGENTS 与项目技能：先核对设备和界面结构；禁止卸载微信或清除微信数据。该规则不妨碍必要的只读日志和已授权的正常调试。

代码实现阶段按任务及项目现行要求运行受影响回归、Debug、签名 Release 与 Lint；本轮纯文档/参考准备只做路径、内容与 Git 差异核对，不构建 APK。现有两个 GitHub Actions 都是手动工作流，正式工作流默认会发布并发送 Telegram，不要把触发发布当作普通验证。

| --- | --- | --- | --- |
