# 朋友圈批量删除 3A-R1：微信 8.0.80 (3220) 原生证据

样本：官方微信 APK，SHA-256 `c35a05d5c13bd43cf1f7ff42c13fab070d21509ab2e233596f776d1afcae52f5`。下列结论来自本轮对该 APK 的 DexSQL Smali 复查。

| 位置 | 实际行为 | 对 R1 的影响 |
| --- | --- | --- |
| `SnsUserUI.E0/r1`、`uw.run`、`h6.e/f/w`、`c6.run` | 首屏异步提交，`r3.H(username)` 可拒绝同作者并发；`h6.e` 返回 void。后续从共享 map 读 last ID；`h6.w` 初始化 map、改写回调注册并调用 `m4.g()`。 | 直接复用 `r3` 和微信 `s1.g`，沿用原生请求保护；不使用共享页面游标、回调或初始化。 |
| `r3.<init>`、`qj6.d/f/h/i`、`r3.onGYNetEnd` | 首屏可携带缓存 MD5，普通页还携带本地 MinId/请求时间；MD5 相同分支可从本地计算游标。 | 模块持有的请求明确从 0 起步，清除该请求的缓存协商字段，避免把缓存差量误当全页。 |
| `r3.onGYNetEnd`、`q3.run`、`r3.J/D/i` | `rj6.p` 非零时可先回调本页，并由 `q3` 新建 continuation 场景。正常插入调用 `w5.h`，随后把末条服务器 ID 写入 `r3.m`；`D()` 读取该值。`i()` 读取 `s`；正常后续页为空且无 `ContinueID` 时可设置该位，`I(II)` 也可能基于本地数量设置该位。 | 自有场景使用原生 continuation 内部计数的上界，确保宿主完成一次回调后由会话自行消费 `ContinueID`，否则用 `D()`；守住重复、逆向或缺失游标。只接收精确实例的回调，原始 ID、作者、时间在宿主解析前捕获，映射在存储回调返回后做。空首屏或 203 隐私边界都不确认历史读完。 |
| `OnlineVideoView.P`、`j1.s/l0/i0/I/P/s0/u0`、`s7.c/d` | 微信通过自己的缩略图内存/磁盘缓存、下载通道及 View 注册更新图片或视频封面；`P(View)` 注销绑定。`u0` 只在资源参数为 `-1` 时跳过占位资源查询；普通 `ImageView` 的 `0` 会落入资源查询。 | 复用现有朋友圈内容解析取 `bs4` 媒体，先在后台用 `j1.s` 读取原生缓存。嵌入选择器没有原生时间线的运行标志；`j1.I` 在标志关闭时会取消普通封面加载。此时注册 View 后提交同一个原生缩略图 worker `y1`，不改宿主全局运行状态，不请求原始图片或视频。 |
| `m4.c/g/w`、`w5.o`、`r2.onGYNetEnd` | `c` 将 ID 写入 `bj4/j.h` 并持久化；`g` 能再次创建 `r2(ID,1)`。`w5.o` 中的 `checkNotDel` 可因队列命中提前退出，服务器有对象而本地不入库。`r2` 的 0/0 删除本地行；errType=4 的 op1 清队列，但非 4 的失败可不清。 | 模块逐目标单次提交原生删除场景，不为它添加微信可重放的待删项。用本地提交记录防止结果未知时重发；已有原生待删项不接管、不清理。 |
| `q2.<init>(JZZ)`、`q2.onGYNetEnd/I/J`、`SnsCommentDetailUI.onSceneEnd` | 原生单条详情接口 `mmsnsobjectdetail`；两个布尔分别控制是否请求浏览计数、是否增加浏览计数。`I` 将 0/0、不可见原因非零且无对象 ID 判为不可访问。 | 两个参数均关闭；提交前用真实对象的 ID、作者和时间验证，确认回调后用该接口复查。远端仍返回对象与本地缓存缺失分开处理。无明确理由的空响应不能确认删除。 |

此前测试动态没有可关联的请求实例、回调或目标 ID。待删队列过滤和旧分页缺口都是已证实能导致“模块找不到”的机制；不能据此倒推那条动态的远端删除结果。本轮不提交任何实际删除请求。

正式签名包只读真机结果：微信 8.0.80/3220 单次打开自动读取四个响应，分别收到 10、10、4、0 条，首屏约 1.16 秒，末页约 2.34 秒；24 条全部核实映射，第四页才满足原生结束条件。最新一条落在微信原生相册当前显示的最新月份。遍历可见记录包含八月、九月及之后的多个历史月份；当前账号没有七月或刚发布的可核对样本。真机对照像素确认原生缓存中的图片和视频封面实际显示，视频角标可见，预览可以单独打开并关闭，勾选仍为零。没有清空媒体缓存，因此 CDN 冷读未专项实测；未执行任何真实删除，先前测试动态的远端状态仍为 `NOT_VERIFIED`。

第二台 3220 设备复查：修复前，四个读取会话均收到 70 个 ID，第八页满足末页条件；首页收到 10 条，却只有 4 条完成缓存映射，另外 6 条到会话结束仍未通过。只读比对该设备的 `SnsInfo`，原生相册中漏掉的九月记录有本地缓存，行、`attrBuf` 中的 `SnsObject`、`content` 中的 `TimeLineObject` 的 ID 和作者一致；后两者的 `CreateTime` 一致，但比行的 `createTime` 晚 2–8 秒。

官方 APK 的 `w5.o` 调用 `SnsInfo.setCreateTime`。这个 setter 在服务器时间比已有行时间晚 0–179 秒时直接返回并保留已有行时间，因此 R1 原先的行时间相等检查会拒绝有效记录。修正后，仍要求行的 ID 和作者与服务器一致；行时间不同时，只有原生 `TimeLineObject` 的 ID、作者和时间三者与服务器对象完全一致，才接受该记录。选择和删除前复核使用同一个服务器时间。未引入时间容差，也未执行真实删除。

同一台设备安装修复后的正式签名包，首页 10 条均映射，八个响应共映射 70 条，待同步与不可读均为 0；末页用时约 3.66 秒。选择器显示 70 条，已在界面核对原生相册中的 9 月 24 日、19 日、11 日以及 8 月和 7 月的动态，勾选为 0。真实删除仍为 `NOT_VERIFIED`。
