# ②-2B-1 热更新 DexKit 开销精准定位

日期 2026-11-03；基线 `main` / `a1bd7b5ac2e4b583489f65be96ae2329998e3174`。仅诊断，无业务修复；结论适用于本次微信 8.0.80 与当前配置。

## 结论

**确认同一运行时身份下重复扫描 `upgrade_response`**：三次独立主进程启动中均先读到缓存缺项，然后实际调用一次 DexKit 查询，三次均返回 0 个原始候选、0 个有效 Hook；查询墙钟分别 879.645、980.915、1163.775 ms，合计 3024.335 ms。发起线程 CPU 分别 30.401、34.032、41.114 ms，合计 105.547 ms；DexKit 可使用其他线程，不能把该数当作查询总 CPU。缓存缺项不是推断依据：每次均有查询开始、返回与候选计数的运行时事件。

直接原因是 [`DisableHotUpdateFeature`](../../app/src/main/java/h/Hchat/hooks/items/hotupdate/DisableHotUpdateFeature.kt) 对 `upgrade_response` 的缓存空列表进入 `findMethod`；零候选时 `DexMethodCache.clear` 移除该键，没有保存“在此完整身份下成功查询但没有匹配”的状态。进程重启后，运行时身份不变但没有结果可复用，于是再次查询。这里的零候选是当前设备查询结果，不代表其他微信版本必然没有目标，也不证明异常、未完成查询或不同 ClassLoader 可以安全复用空结果。

## 方法与样本边界

- 主机源码状态和设备安装包与基线核对一致；设备 Xiaomi 22081212C、Android 15，微信 8.0.80 / 3220；LSPosed 作用域及模块设置未改变。仅在本机忽略目录基线副本加入临时日志；未修改仓库业务源码。诊断构建与原包证书相同，`adb install -r` 保留数据，完成后覆盖恢复原包，并核对其 SHA-256 与原值 `2c0c94ba60addafb3b1a042d9d97b82e2dc6f88b967bac92ac8360a3c27061fc` 一致。没有卸载、清数据、清定位缓存、主动 GC 或触发消息/AI 业务。
- 日志记录 attach 阶段、进程/线程、ClassLoader 的进程内 identity hash、运行时身份的 SHA-256 前 16 位、缓存状态、查询数量/候选数、成功安装数以及单调墙钟和线程 CPU；不记录消息、凭据或身份原文。诊断增加计算、日志开销和额外一次身份计算，绝对耗时仅代表此诊断包。R8、安装和其他进程干扰使其不等同于正式包启动时长。
- 启动时系统进程日志刷新很快，第一轮的早期日志被环形缓冲覆盖；从第二轮开始实时过滤日志，另补一次启动。以下三列对应实时捕获的第二、第三、第四次主进程启动；第三次启动后约 7 秒开始第四次、第四次约 24 秒后恢复原包，因此完整后台区间不等长，但三个定位器、锁和暖机事件均已结束并捕获。它们是三次进程重启，而不是三次清空定位缓存。系统报告 Splash `TotalTime` 为 1845 / 1765 / 1908 ms，不是主页可交互时间。
- 每次主进程记录的运行时身份摘要相同；采样前和各轮后 `patch_meta.info` 及热更新缓存文件哈希相同。两个哈希相同并不能替代完整运行时身份校验，但诊断实际使用的身份摘要亦相同。各次 attach before/after 记录的 ClassLoader 进程内 identity hash 相同；该整数不用于跨进程确认对象相同或证明不会发生后续 ClassLoader 切换。
- 原始日志、环境哈希、启动输出、临时源码、构建日志及可恢复包校验存于 Git 忽略的 `dist/round2_2b_raw/`，不提交。日志按 tag 实时捕获；额外的事后 logcat 快照因环形缓冲覆盖不作为启动早期证据。系统负载、原有网络活动和自动进入的微信子进程未隔离。

| 主进程定位器 | R1 / R2 / R3 缓存与查询 | 原始候选 / 有效结果 / 成功 Hook | 定位墙钟 ms | 发起线程 CPU ms |

| `sync_response_consumer` | 每轮命中，查询 0 / 0 / 0 | 未查询 / 1 / 1，各轮相同 | 8.629 / 9.096 / 6.608 | 3 / 4 / 5 |
| `upgrade_response` | 每轮缺项，查询 1 / 1 / 1 | 0 / 0 / 0，各轮相同 | 879.839 / 981.085 / 1164.116 | 30 / 34 / 41 |

`manual` 定位日志记录的是有效方法，实际 Hook 成功通过随后独立的 `manual_hook_success` 验证；`sync` 成功数在全部 Hook 调用成功返回后记录。`upgrade` 日志中候选为 0，且正常返回，不是异常路径。零候选的精确查询时间见结论；表中定位时间包含缓存读取、过滤和少量日志。缓存命中时未运行 DexKit，故原始候选数量不可得，不应写为零。

本次未观察到身份不符或描述符无效；插桩区分这两种情况与缺项，但列表部分描述符可恢复、部分失效时只报告命中和恢复数量，没有证明所有条目都有效。异常路径不会输出完整定位统计；不能用缺失日志证明查询成功。主进程实际调用 `install` 两次：attach 后首次执行，后续初始化时相同 loader 在 `lateInstalledLoaders` 命中并返回，未发生第二次查询。各轮还有 `:push` 和其他子进程运行同一逻辑；一次可识别的 push 样本也命中另外两个缓存、对 `upgrade_response` 查询一次、0 候选、墙钟 2469.130 ms。子进程结果不能简单加到主进程延迟，跨进程缓存和调度各自独立。

## 锁与功能就绪链

[`ModuleEntry`](../../app/src/main/java/h/Hchat/ModuleEntry.java) 在 Tinker attach before 安装早期拦截，after 验证身份后另起线程；其 `runDexKitTask` 与 `Hchat-Init`、`DexInstallScheduler` 的排队任务使用同一进程内锁。首次热更新安装持锁墙钟 960.436 / 1059.292 / 1255.960 ms，锁等待分别约 0.003 / 0.002 / 0.002 ms。该持锁区间包括身份计算、库加载、全部定位与安装，不全是 `upgrade_response` 查询。

在同一主进程中，初始化线程的另一段直接锁等待 835.124 / 888.800 / 1152.172 ms，随后持锁 3672.388 / 3043.402 / 3062.374 ms。其等待区间与上述热更新持锁区间相交，支持热更新工作导致该线程排队；插桩记录的是获取/释放的线程和时刻，不能单凭它证明对主页首帧或交互的因果影响。稍后的 `wechat_api:warmup` 在调度 worker 上获取锁等待约 0.001 ms，持锁 33.989 / 90.716 / 80.956 ms；排队等待发生在入队到执行期间，**不包括在这些锁等待数字中**。[`WechatApiFeature`](../../app/src/main/java/h/Hchat/hooks/api/core/WechatApiFeature.java) 先建立 API，再安排全局解析，只有流程结束才发布 `DexReady`；此处没有更改时序。

此前 ②-2A 的 `Hchat-HotUpdate` 原生采样栈落在无符号 DexKit；本轮确认对应路径真实执行 `upgrade_response` 查询，但未将每一个 native 采样地址逐一映射到这次查询，也没有测量全部 native worker 的 CPU。因此不能声称它解释了全部启动 CPU，也不将三个墙钟时间当成纯 CPU 时间。

## 最小修复建议与待验证

建议先在 [`DexMethodCache`](../../app/src/main/java/h/Hchat/dexkit/DexMethodCache.kt) 与 `hookUpgradeResponse` 的边界设计可区分的状态：有效描述符、**完整且成功执行查询后确认为零候选**、未查询/身份不符、描述符失效、查询异常。仅为有明确成功标志、完整版本/APK/DEX/Tinker 身份及定位器规则版本的零候选结果提供可失效的复用；缺项、异常、部分加载及身份不完整时继续原查询/恢复。是否复用“有候选但签名校验后全无有效方法”需单独证明，不能与本次零原始候选合并。升级定位器规则、APK/DEX/Tinker 变更和 ClassLoader 无法安全解析时应失效。应验证不同进程的 FastKV 可见性、并发写入、类加载器差异和结果恢复；不可因负缓存抑制新的有效 Hook 或跨身份复用。早期 Tinker flags/loader 拦截继续保持原位置，DexKit 串行门、代次取消与 `DexReady` 保持原语义。

候选方案仍需用户确认后另立实施：覆盖同身份重复启动、异常后重试、空结果、有效结果、部分失效、跨进程竞争、Tinker 换代、早期 Hook 与旧代次取消，并在相同设备/配置下比较扫描次数、工作线程 CPU、首帧及功能就绪。此轮没有实施负缓存，不预先宣称收益。真实交互改善、全部 native 工作线程 CPU、身份变化后重扫，以及其他微信版本均为 **NOT_VERIFIED**。

既有 `scripts/tests/phase_b/run.js` 在基线通过，覆盖身份策略和 DexKit 冷/热、30 秒回收及惰性重开；它不覆盖本次三个定位器的负缓存或现场观测。相关源码还包括 [`DexCacheIdentity`](../../app/src/main/java/h/Hchat/dexkit/DexCacheIdentity.kt) 和 [`DexInstallScheduler`](../../app/src/main/java/h/Hchat/hooks/core/DexInstallScheduler.kt)。
