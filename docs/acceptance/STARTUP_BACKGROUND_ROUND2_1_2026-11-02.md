# WeiPlus 第二轮 ②-1：启动与后台资源验收

日期：2026-11-02 至 2026-11-03。起点为 `main` / `ed183f8c670b42780db7bd0574344d8e1353ca6d`；开始时工作区干净。本记录关联提交为最终源码提交。

## 原因与范围

- 模块初始化原本无条件加载 `libsilk_codec.so`。JNI 方法均属于 `SilkCodec`：构造实例时统一通过 `SilkLibrary` 按需调用既有 `NativeLibraryLoader`，沿用框架提供的模块 APK、ARM64、ZIP 条目与 CRC 校验、文件锁及成功缓存。失败不缓存，可再次尝试；没有音频需求时仅登记宿主 Application 的弱引用，不读取或加载音频库。
- `AudioTransformBridge`、`WeChatVoiceApi`、`AacCodec` 内部转换、自动回复转换、语音转发和收藏语音都经过同一构造入口。音频页面保存校验与收藏语音确认发送移到工作线程。确实匹配到语音需求时可异步预热；红包及收款的主线程语音步骤在库未就绪时异步等待，并沿原有步骤顺序继续，取消/销毁会拒绝旧回调。进退群语音在既有后台工作线程先完成加载，再维持原有主线程发送及有效性检查；普通收藏不加载 Silk。相关调整仅服务音频就绪和原有步骤顺序，没有重构通用自动回复队列或公共线程池。
- 朋友圈自动刷新原为启用后每秒检查一次，即使间隔为数分钟。现在只安排下一次到期或时间窗口打开时的检查；配置变更、时钟/时区及前台恢复会重新计算。首次延迟采用单调时钟；失败仍按原规则约 30 秒重试；零间隔保持原先每秒最多一次的节奏。启用时才注册时钟和前台监听，关闭/销毁注销并关闭定时线程；跨重建的在途请求通过完成通知协调，既不重叠也不为等待每秒轮询。
- 上述互斥覆盖调度器对 `refreshTimeline()` 的调用和提交。现有 SNS API 返回的是请求是否提交，并未向此调度器报告微信网络请求的最终完成；因此不能据此声称网络层不会同时存在多个尚未完成的请求。
- DexKit 的加载、热缓存、30 秒空闲释放、Tinker ClassLoader 和早期 Hook 时序没有改动。没有新增常驻服务、WakeLock 或周期性精确闹钟。

主要源码：`ModuleEntry.java`、`SilkLibrary.java`、`SilkCodec.java`、`WeChatFavoriteApi.kt`、`MomentsAutoRefreshFeature.kt`、`MomentsRefreshScheduler.java`、音频页面和语音转发入口，以及红包、收款、进退群中直接涉及语音就绪的调用点。新增 `scripts/run_performance_round2_tests.cjs` 及 `scripts/tests/performance_round2/`，扩展语音兼容回归。

## 真机方法与边界

设备 Xiaomi 22081212C / Android 15；官方微信 `com.tencent.mm` 8.0.80 / 3220；LSPosed 中 `h.Hchat` 启用且作用域为官方微信。基线签名 APK SHA-256 `94b1e73fa9fb18da1fd2438e9f3299d72dc720d2b3c4b6dc3f2b5fd6555d0110`；最终 APK SHA-256 `2c0c94ba60addafb3b1a042d9d97b82e2dc6f88b967bac92ac8360a3c27061fc`，覆盖安装后设备 APK 与本地 SHA-256 一致。采样前后检查 292 个模块 FastKV 槽位：178 个非定位缓存槽位哈希未变；55 对定位/运行时缓存槽位发生变化，其余缓存槽位未变。未主动 GC、未卸载或清数据、未发送消息，也未手动修改生产配置。

朋友圈自动刷新配置槽位为空，默认关闭；因此本机三轮不是功能启用态 CPU 对照，启用态调度由可控时钟与隔离 Runtime 回归覆盖，真实微信中启用时的 CPU 变化 **NOT_VERIFIED**。未关闭原有功能制造收益。启动命令终止微信进程后启动，系统报告的 `TotalTime` 指向 WeChatSplashActivity；这不是主页可交互时间。返回主页的 `WaitTime` 是恢复已有任务的系统耗时。微信无障碍树为空，无法直接用无障碍节点确定精确的首次可交互时刻；后续补充使用离线截图识别和点击确认，得到含探针开销的上界，见下表。

每轮保持同一聊天、10 对固定滚动，使用 `gfxinfo` 重置帧统计并保存完整 `framestats`；在前台静置约 45 秒、后台约 60 秒前后采集 `/proc` 线程和进程计数、`top`、PSS 与电源状态。`getconf CLK_TCK` 为 250；CPU 百分比以单核 100% 计算，区间包含采集开销。每 10 秒注入一次 `KEYCODE_WAKEUP`，采样点均记录电源状态；独立辅助检查每 5 秒连续 30 秒均为 Awake，但不能据此保证所有静置区间的每一刻都清醒。基线与最终的第二轮滚动中均额外截屏检查页面，截图已删除，该操作可能扰动该轮 jank。

设备还出现一次最终包首次启动 `tablet_tinker_attach_after:runtime_identity_changed`，模块随后主动失效，DexKit 未映射；同一现象在修改前试运行 PID 12985 和更早设备日志中也出现，普通重启后恢复。该次原始数据单独保存于 `dist/round2_1_raw/final_invalid_start/`，不混入有效样本；本轮未修改相关身份或 Tinker 逻辑。现象根因未确定，不能把历史出现解释为已修复。

微信 Tinker 的 `patch_meta.info` 元数据时间为 23:08，位于原始基线与最终采样之间；上述定位缓存变化发生在身份失效和重启之后。各个缓存变动的原因和每轮命中状态没有逐项证据，因此不能认为原始前后采样的热缓存条件完全相同。另用原始基线 APK 在当前 Tinker 状态补采三轮，与最终包采样对照；补充基线在上一候选包之后、最终包采样之前取得，仍有系统状态和时间漂移，原始基线样本不丢弃。

## 音频真机探针与未验证事项

最终 APK 仍安装在手机时，独立 Android ARM64 `app_process` 探针使用生产加载器源码、模拟框架身份和最终签名 APK 中的 `libsilk_codec.so`：无需求时映射为零；故意提供不可读模块路径后第一次加载失败，改为正确路径可重试；32 个并发请求均成功；合成 WAV 经 `wavToSilk`、`silkToPcm`、`AacCodec.autoToSilkCompat` 和 `autoToPcmCompat` 转换均返回 0，输出非空。探针及生成文件已从手机删除。由于框架身份由探针模拟且加载器从源码单独编译，它不等于最终 APK 在微信进程内的完整 JNI/业务链路验证。

微信真实进程的无需求不加载、模块初始化和前台聊天滚动已验证；未发送消息，因此真实语音发送、自动回复、语音收藏转发和微信内音频转换全链路仍为 **NOT_VERIFIED**。朋友圈启用态真实后台 CPU 与刷新提交同样未测：当前生产开关关闭，用户禁止擅自修改配置。上述业务和启用态可由用户独立验收；不能用隔离回归或源码调用减少替代这些实测。


完整原始性能输出、失败和成功的回归日志、采样脚本、签名信息、Lint 报告、R8 mapping 及探针源码位于忽略的 `dist/round2_1_raw/`，不提交包含设备运行信息的原始输出。最终 APK 位于 `dist/Hchat-1.2.0-release-signed.apk`。最终提交、远端和工作区状态见交付消息。
