# AI 聊天 R1：微信原生语音转写诊断

目标为微信 8.0.80（3220）。上一轮在真机上直接调用模块转写接口，两个已有语音样本均未得到转写文本；其后设备发生一次软重启，无法确定是否与当时的调试方式有关。没有保留下可用于判断具体失败原因的回调错误码，因此不能把转写视为已通过。

本轮静态核对：

- 微信 `com.tencent.mm.ui.chatting.component.gp.w0` 的原生入口把消息 ID、会话和文件标识分别写入 `ExtTranslateVoiceEvent.g.b/g/a`；普通私聊场景 `f=1`，群聊场景 `f=2`。对应反编译来源位于本机逆向资料第 12 卷。
- `uv.p0.Fj` 的 Java 与 Smali 均显示，文件标识来自消息的 `getImgPath()`；分别见第 17、19 卷。
- `co4.c` 对 opcode 0 在已有活动任务时返回失败；opcode 1、2、3 涉及取消或清理。本模块仅使用 opcode 0，且模块内转写入口串行化。Java 与 Smali 见第 16 卷。
- `IEvent.e()` 经 `EventPoolImpl.c` 返回的是是否存在监听器，而不是 `co4.c` 是否接受任务；见第 18 卷。因此日志使用 `listenerPresent`，不能把返回 true 记作受理成功。没有完成回调时，忙碌与其他超时原因仍无法区分。
- `a9.b` 表示完成，`a9.c` 为结果状态，`a9.d` 中的 `d/e` 为错误码和错误类型。模块日志只记录监听器是否存在、场景、完成状态、错误码和文本长度，不记录语音、转写正文或联系人；日志不能证明任务已被受理。
- `VoiceTransText` 优先按消息 ID 查询，并按文件标识回查。完成回调为空时再次查询缓存。

本轮可用设备上安装的是上一轮测试前恢复的旧调试包，且没有独立 AI 聊天配置；无法据此还原用户曾见到英文或思考内容时的配置、请求或响应。待有一条新收到且音频完整的样本时，应对照同一条消息的微信手动转写、模块受理状态、完成状态与本地转写表结果；如再次发生系统异常，停止该调试路径并保留脱敏日志。
